# Training sessions and attendees

This batch migrates seven methods while preserving request linking, session transitions, attendance history, credential progression, subscriptions and notifications. All methods require a live website session or active database bot token. Training staff means a positive `training:approve_request` or `training:mark` grant, or superadmin; bots retain superadmin authority. Session creator, request handler and history actor IDs are null for bot actions. No schema migration is needed.

| Endpoint | Methods | Contract |
| --- | --- | --- |
| `/api/training-sessions` | GET, POST | GET returns cursor-paginated sessions. POST requires staff and creates a draft or scheduled session. |
| `/api/training-sessions/{id}` | GET, PATCH | GET requires staff or the user's own active attendance in a non-proposed/non-cancelled session. PATCH requires staff and preserves omitted fields. |
| `/api/training-sessions/{id}/attendees` | POST | Staff adds a user, optionally linking or advancing a training request. |
| `/api/training-sessions/{id}/attendees/{attendeeId}` | PATCH, DELETE | Staff records attendance or cancels attendance. DELETE retains the record and returns `data:null`. |

PUT on session and attendee resources is removed. The collection's old `{sessions,isStaff}` wrapper becomes `{data:Session[],meta:{limit,nextCursor,isStaff}}`. Detail GET returns `{data:Session,meta:{isStaff}}`. Other successes use `{data,meta:{}}`: POST session/attendee returns 201; PATCH returns 200. Attendee mutation responses return the attendee directly, without old `attendee`/`removed` wrappers. Errors share `{error:{code,message,details,correlationId}}`.

GET collection accepts only `limit` (50 by default, capped at 100), `cursor` (exclusive positive Int32 ID), optional positive Int32 `trainingId`/`trainerId`, `status`, and explicitly zoned `from`/`to` timestamps. `from` is inclusive, `to` exclusive and `from < to`. Results are descending ID with actual lookahead. Unknown/repeated filters and invalid timestamps are 400. Staff sees all sessions; other users are filtered before pagination to their active attendee records and non-proposed/non-cancelled sessions. Their nested attendee array contains only themselves. Other methods reject all query parameters. Other-user reads audit returned trainer/attendee IDs, excluding self and lookahead; a read-audit failure returns 500.

Session DTOs retain session scalar fields, the training catalog record, minimal trainer `{id,username,avatarUrl}`, attendees with minimal users and `{id,status}` request references, and the existing `server` display string. All actual timestamps serialize to UTC Z. No authentication accounts, email addresses or permission grants are included. The website gathers all list pages before sorting by start time; date filters explicitly use UTC date boundaries.

POST session requires numeric `trainingId` and an eligible numeric `trainerId`; optional fields are `status` (`proposed` default or `scheduled`), nullable zoned `startsAt`, nullable `durationMinutes` (1–1440; omitted/null creation uses the training default), nullable `specialInstructions` (at most 4000 trimmed characters), and unique numeric `attendeeUserIds`. A scheduled session requires a start time. Removed `confirmed` is replaced by `status`. The training must be active and require sessions. Users, eligible trainer and active training are rechecked in the mutation transaction. Active pending requests cannot be attached to a confirmed session, and a user cannot hold another open session for the same training.

Session PATCH accepts a nonempty subset of `trainerId` (nullable), `startsAt` (nullable zoned timestamp), `durationMinutes` (nullable), `specialInstructions`, and `status`. The state machine remains proposed → scheduled → in_progress → completed, with cancellation from open states; completed/cancelled are terminal. Active scheduled states require trainer/start. Linked pending requests block scheduling/starting; scheduled attendees must have attendance recorded before session completion. Session and linked-record updates retain concurrency checks. Starting an approved request updates its credential to in_training and records history; it never grants qualification automatically. Cancellation resets reminders and releases request links for rescheduling while leaving requests open.

POST attendee requires numeric `userId`; optional `trainingRequestId` is numeric/null, `notes` is nullable trimmed text up to 4000 characters, and `advanceTraining` is boolean. Omitted request ID auto-selects the latest active request; explicit null skips auto-selection. Advancement can create a request and progress pending→approved or approved→in_training, maintaining credential/history/system-message consistency. Explicit nonexistent request IDs return 404 even when advancement is requested. Completed/cancelled sessions, duplicate attendees, mismatched requests and other open-session assignments remain conflicts.

Attendee PATCH requires `status` (`scheduled`, `attended`, `completed`, `absent`, `cancelled`) and optionally `notes`/zoned `expectedUpdatedAt`. DELETE accepts an optional body containing only `notes`/`expectedUpdatedAt`. Stale expected timestamps return 409; restoring cancelled attendance checks for another open session. Attended/completed states set attendance timestamps and may start an approved request/credential, but qualification remains separate. PATCH returns refreshed linked request state after progression.

Mutation audit, linked system messages/subscriptions/history, website inbox messages and relevant bot outbox events all share the Serializable Prisma transaction. Audit snapshots contain IDs, statuses and timing, excluding instructions/notes. Realtime inbox/profile/chat publication runs after commit; publication failure does not turn a committed mutation into a failed response. Notification or audit database failures roll back the mutation.

Tests: `tests/api/training-sessions.test.ts` covers all methods, session/bot authentication, staff rights, strict queries/payloads, pagination/read scope, lifecycle constraints, concurrency, notifications and audit failures. `tests/api-integration/training-sessions.test.ts` covers the complete scheduled lifecycle, request/credential progression, cancellation/rescheduling, privacy scopes, token revocation, timestamp guards and transaction rollback using isolated Prisma-managed PGlite. Training-request and user-training endpoints remain subsequent batches.
